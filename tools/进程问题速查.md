# 进程问题速查：症状 → 原因 → 改法

对象：`ttf2_coyote` v2.20.2（泰坦陨落 2 × 郊狼插件）
适用范围：所有「附加不到进程 / 附加错了进程 / 附加上了但读不到」的问题

## 三分钟排查流程

1. **看状态卡**：`数据源定位：<进程名> (PID <pid>) / engine.dll=0x<地址>`
   - 显示 `未连接进程` → 看第 1、2、7 条；
   - 显示进程名但 `engine.dll=未找到` → 看第 3、6 条；
   - 显示正常但读数不对 → 不是进程问题，看第 4 条（链的写法）。
2. **看日志里那条 `自检：…`**（v2.20.0 起自动打，30 秒最多一条）—— 它已经把原因和建议写进去了，直接对照本表。
3. **手动确认**：游戏运行时在插件目录执行 `python tools\probe_process.py`，它会列出所有候选进程的
   「有无窗口 / 有没有加载 engine.dll / 基址」并给出该填什么。

---

## 1. 完全找不到进程

**日志原文**
```
自检：没找到游戏进程 —— 游戏没启动，或 exe 被改名了（当前配置：auto；探测范围：进程名含 titanfall / northstar）…
数据源 未连接进程
```
**原因**（三种，按概率）
1. 游戏真的没开（或还在启动器里没点开始）；
2. 「进程 / 默认模块名」里手填了一个不存在的名字 —— 常见错法：带路径、带引号、带 `.exe` 之外的尾巴、打错字母；
3. 游戏 exe 被改名了（整合包、私服包、"Titanfall2 - 副本.exe"），auto 的三个候选全对不上。

**改法**
- 先 `python tools\probe_process.py` 看真实进程名（它按 `titanfall` / `northstar` 关键词匹配，改名也认得出）；
- 名字不标准就把「进程 / 默认模块名」**填成那个真实名字**（只填文件名，不带路径）；
- 名字就是标准的三个之一，就填 `auto`。

**验证**：状态卡出现 `数据源定位：<名字> (PID …)`。

---

## 2. 开了 Northstar 却填了 `Titanfall2.exe`（或反过来）

**症状**：昨天能读，换了启动方式就读不到；或自检报
```
自检：进程名不匹配 —— 你填的 Titanfall2.exe 没有对应进程；引擎在 NorthstarLauncher.exe（pid 192）。请改成 NorthstarLauncher.exe（这个名字在 auto 候选里，直接填 auto 也可以）
```
**原因**：引擎宿主会换人。本机实测：
- `NorthstarLauncher.exe` 启动（含 `-profile=R2Titanfall -vanilla`）→ 引擎在 **`NorthstarLauncher.exe`** 里；
- 官服直启 / Steam 按钮 → 引擎在 **`Titanfall2.exe`** 里。

**改法**：填 `auto`（两个名字都在候选里，自动挑），或者填当时那条路径对应的名字。

**验证**：同第 1 条。

---

## 3. `找不到模块 engine.dll`

**日志原文**
```
找不到模块 engine.dll —— 指针链里写的模块名必须真的加载在当前进程里（当前附加的是 Titanfall2.exe；链里若写了别的游戏的模块名请改掉）
```
**原因**（三种）
1. **附加到的进程里没有引擎**：最典型是直启 `Titanfall2.exe` 后卡在 EA 授权（`Core\ActivationUI.exe` 弹「登录」），
   此时进程存在但 `engine.dll` 还没载入；
2. 附加到了**专用服务器**（`r2ds.bat` → `NorthstarLauncher.exe -dedicated`）：服务端不跑客户端逻辑；
3. 链里写的模块名在当前进程里叫别的（游戏换分支/大版本更新后引擎 dll 改名）。

**改法**
- 情况 1：等授权完成、真正进到游戏画面（自检会提示「进程在、引擎不在…等授权完成」）；
- 情况 2：开客户端，别开 `r2ds.bat`（自检会提示「这个进程没有窗口，可能是专用服务器」）；
- 情况 3：`python tools\probe_process.py` 看实际加载的模块名，把链里的 `engine.dll` 改成实际名字；
  或者**把链里的模块名去掉**（写成纯偏移），让它退回「宿主 exe 主模块」——但注意第 4 条的坑。

**验证**：状态行 `engine.dll=0x……` 有地址。

---

## 4. 链里不写模块名（纯偏移）→ 换启动方式后全是垃圾读数

**症状**：能附加、`数据源定位` 正常，但读数荒谬（负数、巨大值），日志
```
连续读到无效数据：…
```
**原因**：纯偏移链（`0x111E1E68 -> 0x18`）的基址取的是**宿主 exe 的主模块**。
Northstar ↔ 官服切换时宿主 exe 变了，基址跟着变，偏移全部作废。
（本机 Northstar 会话里 `engine.dll` 基址 0x7FFF92E50000，官服会话也是同一个 —— 但宿主 exe 基址不同。）

**改法**：给链补上模块名前缀，写成 `engine.dll+111E1E68` 这种形式。这样基址永远相对 `engine.dll`，
换启动方式不用改配置。

**验证**：切一次 Northstar/官服，读数仍然正常。

---

## 5. 多开两份客户端，插件只认一份

**症状**：自检报
```
…；另有 1 个进程也加载了引擎（多开？），插件只认有窗口的那一个
```
**原因**：同名进程无法靠名字区分。插件按「有可见窗口优先」挑，另一个窗口被忽略。

**改法**：玩的时候只开一份客户端。真要同时跑两份、且要控制第二份，需要给插件加 PID 指定（当前不支持）。

---

## 6. 专用服务器被当成正常宿主

**症状**：只开了 `r2ds.bat`，自检说「引擎宿主是 NorthstarLauncher.exe」，但读出来全是无效数据；
该进程没有窗口。
**原因**：`-dedicated` 服务端同样加载 `engine.dll`，从模块表上看和客户端一样，唯一的区别是**没有窗口**。

**改法**：开客户端（客户端加服务端同时跑时，插件会靠「有窗口优先」选客户端）。

---

## 7. `OpenProcess 失败（err=5）`

**日志原文**
```
OpenProcess 失败（err=5），请以管理员身份运行 DGHub
```
**原因**：读进程内存需要 `PROCESS_VM_READ | PROCESS_QUERY_INFORMATION`。游戏以管理员权限启动、
DGHub 是普通权限时会被拒（err=5 = 拒绝访问）。

**改法**：**以管理员身份运行 DGHub**（右键 → 以管理员身份运行），或让两者权限一致（都用普通权限）。

**验证**：日志不再出现 OpenProcess 失败，状态卡出现 PID。

---

## 8. 游戏重启后读不到（句柄/基址失效）

**症状**：`数据源 未连接进程 ｜ 游戏进程可能已关闭，或句柄/模块基址失效（换启动方式、重启游戏后需重新解析）`
**原因**：游戏进程换了 PID，旧句柄和模块基址全失效。
**改法**：通常**不用管** —— 插件下一次读取会自动重开句柄、重新解析模块基址（`_reopen_next` 机制）。
若长时间不恢复：切一次数据源（模拟 ↔ 内存）或重载插件。

---

## 9. 进程名带空格，被截断成半截

**症状**（v2.19.0 之前的插件）：`Die cry.exe` 这种带空格的 exe 名，链 `"Die cry.exe"+0x1234` 被解析成模块名
`cry.exe`，链直接废掉。
**原因**：旧的模块名正则不允许空格。
**改法**：升级到 v2.19.0+（已支持带空格与引号的模块名）。这属于其它游戏接入的问题，
详见 [`tools-mz/接入Die cry-修改方法.md`](../tools-mz/接入Die%20cry-修改方法.md)。

---

## 10. 用包装器 / 兼容层启动，进程名不是你以为的那个

**症状**：游戏明明在跑，`probe_process.py` 却只看到陌生的进程名（包装器自己的名字）。
**原因**：Sandboxie、部分第三方启动器、虚拟机直通会把游戏跑在自己的宿主进程里。
**改法**：把「进程 / 默认模块名」填成**实际承载引擎**的那个进程名（`probe_process.py` 会标出哪个进程加载了
`engine.dll`）。名字不在 auto 候选里就必须手填，auto 永远连不上。

---

## 11. 32 位游戏（RPG Maker XP/VX/Ace 等）—— 本插件不支持

**症状**：能附加（DGHub 是 64 位，读 32 位进程内存本身可行），但按 8 字节读指针，链解出来全是错的。
**原因**：插件的指针链解析按 64 位指针宽度实现。
**改法**：这类游戏要么改成读 JS/文件（RPG Maker MV/MZ 的做法，见 `tools-mz\`），要么另做一个 32 位源。
把「进程 / 默认模块名」填对也解决不了指针宽度问题。

---

## 附：这些问题的判据一览

| 判据（状态卡 / 日志） | 结论 | 该改的地方 |
|---|---|---|
| `数据源定位：未连接进程` | 没附加成功 | 进程名（第 1、2、7 条） |
| `engine.dll=未找到` | 附加上了但没引擎 | 等授权 / 别开 dedi / 改链里模块名（第 3、6 条） |
| `engine.dll=0x…` 有地址，但读数荒谬 | 链的写法或偏移错 | 链补模块名 / 重新标定（第 4 条） |
| `OpenProcess 失败（err=5）` | 权限 | 管理员运行 DGHub（第 7 条） |
| 自检说「进程名填错了」 | 填的名字有进程但引擎不它里面 | 改成自检给出的名字（第 2 条） |
| 自检说「多开」 | 同名多进程 | 只开一份（第 5 条） |

> 一句话判据：**「哪个进程加载了 `engine.dll`，就附加哪个」** —— 其余都是这句话的推论。
